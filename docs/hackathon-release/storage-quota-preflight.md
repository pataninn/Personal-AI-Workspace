## Finding

Task 3.2 needs one logical-byte rule across relational content, workspace files, and retained recovery copies. Relational writes can update quota state in the same PostgreSQL transaction as their resource write. Workspace promotion and cleanup cannot: they cross PostgreSQL and filesystem boundaries, so they need a durable reservation before filesystem side effects, then a verified settle or a retained unknown reservation for reconciliation.

## Smallest design consistent with these boundaries

1. Define and version one logical-byte measure before adding counters:
   - Treat each selected text or content-bearing JSONB field as the quota unit. Use PostgreSQL octet_length(text) for text and octet_length(jsonb::text) for the full normalized serialized value of a content-bearing JSONB field (including its keys and embedded structure). Include each retained persisted copy (for example, proposal plus promoted file). Exclude indexes/tuple overhead and standalone structural columns such as UUIDs, hashes, timestamps, and status fields; exclude shared curated templates.
   - For files and recovery snapshots, use lstat/stat.size for regular files. Count retained recovery files in addition to live project files. Do not substitute character count, estimated disk allocation, or file count.
   - Keep all limits and counters as integer bytes; 5 GB is exactly 5,000,000,000 bytes.

2. Expose the policy through one application-layer storage-quota port used by write use cases; keep SQL and row locks out of controllers. The TypeORM adapter should support the existing transaction boundary, and filesystem gateways should receive durable-reservation operations without holding a DB transaction through I/O. For DB-only create/update/delete, use the same QueryRunner transaction as the source row. Acquire the owner’s account_limits serialization row first, calculate old/new byte deltas from canonical stored values, reject positive growth when limit != null and used + reserved + delta > limit, then write the resource and its accounting reference/counter in that transaction. Existing conversation/task/home repository transactions are usable boundaries; facts and any other direct autocommit writes must be converted. Idempotent replays add no second charge. Keep the lock order consistent before project/resource/action-ledger row locks.

3. For filesystem writes, persist an idempotent reservation with owner, trusted project/root reference, operation key, expected current hash/size, intended content size, and recovery-copy delta. Check quota under a short account_limits lock, commit that reservation, then perform filesystem I/O. Finalize only after verifying the resulting target and recovery files; update the resource reference/counter and clear the reservation. A known failure may release a reservation only after proving no persistent side effect remains. An ambiguous write, backup, unlink, or process/DB outcome keeps the reservation charged/pending until reconciliation establishes the actual state. Never hold a DB transaction or account row lock over filesystem operations.

4. For unknown-size streams, never write unbounded output and count afterward. Enforce a hard transient staging cap, obtain the exact staged byte size, reserve that exact promotion growth before moving it into persistent storage, and reject when the source length cannot be established. For known generated text, calculate UTF-8 bytes before the persistent write. Over-limit accounts may read, delete, or shrink; lowering a limit below current use never deletes content. A delete that retains a recovery copy may not reduce usage until that copy expires or is purged.

5. Reconcile against canonical DB rows, trusted project roots, retained recovery manifests, and outstanding reservations. Existing accounts require a backfill before non-null limits can enforce correctly; never initialize existing file usage to zero because no ledger row exists. Use owner/project references, not caller paths; reject symlinks/reparse points and fail closed on unreadable/missing roots or unknown ownership. Preserve pending reservations for in-flight filesystem work. The current project-removal job stores project/run IDs but not a retained owner/root charge, so its storage-accounting reference must survive deletion of the project row. Monitor physical disk space separately; logical quota is not a physical disk guarantee.

## Transaction integration check (2026-10-19)

The new `TypeOrmStorageQuotaRepository.runDatabaseMutation(transaction, ...)` accepts a QueryRunner-compatible transaction and does not create a second runner for relational writes. Its lock order is `account_limits FOR UPDATE` → storage totals/references → caller mutation/resource rows. The existing active-principal guards in `TypeOrmActionLedgerRepository.executeAtomically`, `TypeOrmHomeChangeProposalRepository.createDraft`, and `TypeOrmProjectFileAccess.execute` use `users FOR SHARE`; keep that guard first, then acquire `account_limits`, then storage rows, then target/task/proposal rows. This does not require upgrading the user-row lock. The quota wrapper must run before existing resource-row locks so an account → limits → content order is maintained.

Filesystem integration cannot be nested into the current file-access callback. `TypeOrmProjectFileAccess.execute` starts a `DataSource.transaction`, locks the user and project, and awaits its `action` callback before commit; `ProjectFileActions` callbacks perform gateway reads/writes/removes and document conversion. `StorageQuotaFileMutation` calls repository methods that create their own short QueryRunner transactions for reservation and settlement. Calling it inside that callback would keep the outer connection and user/project locks across filesystem I/O while consuming another pool connection for the reservation. Refactor the boundary so trusted-root resolution uses a short transaction, then re-check the active principal with `users FOR SHARE` inside the reservation transaction before taking `account_limits`; commit the durable reservation before filesystem I/O, then settle in another short transaction. Do not carry the original file-access transaction, project row lock, or account row lock into the filesystem phase. Project removal must coordinate against pending reservations through durable state rather than retaining project-row locks during filesystem work.

`TypeOrmProjectRemovalRepository.remove` also calls `recoveryCleaner.quarantine()` while its QueryRunner transaction is open. In that same transaction it inserts `project_removal_jobs` through `this.dataSource.query(...)` instead of the existing `runner.query(...)`, causing an unnecessary second pooled connection and keeping the job insert outside the transaction. Use the open runner for that transactional insert; the post-`runner.release()` job cleanup may remain a DataSource call. The removal behavior preserves the authoritative project folder after deleting the project row. Storage wiring must therefore retain the folder's charge under an owner/root reference independent of `projects`, and move recovery quarantine I/O outside the database transaction; release the retained-root charge only after verified deletion. The storage reference schema has no project-row foreign key, but the current project-removal code does not yet transfer or maintain that reference. These are integration prerequisites, not implementation or test evidence.

## Durable retained-root mapping decision (2026-10-19)

The additive `storage_root_mappings` manifest is the smallest safe way to preserve the authoritative folder's accounting identity after project metadata is deleted. `project_removal_jobs` only coordinates temporary recovery cleanup and is deleted on completion; it cannot be the source of truth for a surviving project folder. The current `WorkspaceBoundaryAdapter.resolveProjectRoot` resolves managed roots only from the owner UUID, project UUID, and exact `projects/<project UUID>` relative root, while legacy resolution is limited to the configured legacy owner and a checked relative root. A retained-root resolver must use the persisted mapping as trusted input and apply those same boundary checks; it must never accept a request path or store an absolute host/container path.

Required mapping invariants:

- Keep `(owner_id, root_key)` stable and immutable. The current 0030 draft uses `projects.relative_root_key`, a normalized, path-shaped canonical overlap key, as this internal identity. It can remain without conversion as long as it is used only for equality, joins, and resource-reference identity; no code may parse it, join it to a filesystem path, expose it as a path, or treat it as the trusted locator. Filesystem resolution uses only persisted `owner_id`, immutable `locator_project_id`, `storage_kind`, and canonical `relative_root`, followed by the existing workspace-boundary checks. Preserve `storage_kind` and `relative_root` after retention. For managed roots, `relative_root` remains exactly `projects/<original project UUID>`; legacy roots remain limited to the pinned legacy owner and checked containment/reparse rules.
- Constrain `storage_kind` to `legacy|managed`, state to `active|retained`, and enforce `active => project_id IS NOT NULL` and `retained => project_id IS NULL`. Use a composite `(owner_id, project_id) -> projects(owner_id, id) ON DELETE RESTRICT` foreign key (the unique owner/id index already exists); a project-only FK would allow an owner/root mapping to point at another owner's project. Make the owner FK `ON DELETE RESTRICT` as well. User or project deletion must not cascade away the only ownership manifest while files may remain; explicit verified filesystem cleanup must precede account deletion.
- Backfill one attached mapping for every existing file-backed project, including archived projects and the existing legacy root. Planning-only projects with a null storage root get no mapping. Mapping state `active` means it is still attached to a project; it does not mirror the project's active/archived UI status. Serialize root allocation/removal under the established per-owner root lock after the account-limit lock, then compare new roots against attached and retained mappings with the same storage_kind, using the existing project-root overlap normalization within that namespace. Within the container, legacy roots resolve under /workspace and managed roots under the fixed /account-workspaces root; WorkspaceBoundaryAdapter verifies each target and rejects same-directory or ancestor/descendant aliases there. Task 8.1 must separately verify that the host bind sources are physically distinct and non-overlapping, since the runtime adapter cannot prove host-source relationships. For a valid mount configuration, overlap checks do not cross storage kinds: in particular, legacy . cannot block a managed projects/<UUID> root. Reactivation follows the same kind-scoped rule. A path cannot be reassigned or overlap another root of its kind until the old root's physical removal is verified. The existing active-project index alone does not enforce this rule.
- On removal, take locks in the established order: active-principal guard, `account_limits`, per-owner root-allocation lock, root mapping/reservation rows, then project/resource rows. Reject removal while a reservation for that root is pending or has unknown outcome. In the same database transaction, transition the mapping to `retained` and clear its project association before deleting the project row. Do not hold those locks during quarantine or other filesystem work. The retained mapping and its file references survive deletion of the transient removal job; only a verified root deletion can release their byte charge and remove the mapping.
- Missing, unreadable, noncanonical, symlink/reparse, owner-mismatched, or otherwise unsafe roots remain `unavailable`; they are never treated as empty or as a zero-byte deletion. If a project root was removed from the database before this manifest exists, the remaining opaque references and removal jobs (which carry project/run IDs, not a trusted root locator) do not reliably establish its former owner/path. Keep the affected account unavailable until a trusted inventory can establish each surviving root; do not mark the migration/backfill ready by assuming no such roots remain.

This is a source-based design decision, not evidence that the migration or lifecycle has been implemented or tested. Required tests include populated migration/backfill, ownership and FK rejection, active-to-retained transition committed atomically with project deletion, restart after the removal job is purged, pending/unknown reservation blocking, retained-path overlap blocking, and verified-vs-missing/unsafe root cleanup.

## Recovery-root accounting and project-removal decision (2026-10-19)

Keep recovery copies in the existing separately configured `RECOVERY_ROOT` (currently defaulted to `/var/lib/personal-ai/recovery`). Release architecture §2.2 explicitly keeps recovery data outside the workspace and requires cleanup from an owner/project manifest. `WorkspaceMutationGateway.writeBackup` writes `run-<run UUID>/<proposal hash>/<operation UUID>/<file>.bak`; the `BackupCheckpoint.reference` is relative to `RECOVERY_ROOT`. `ProjectRecoveryCleaner` moves the whole `run-<UUID>` directory to `.removed-run-<UUID>` and later restores or purges it. Do not move new backups under the project tree: that would contradict the protected recovery boundary, make root removal affect recovery copies, and couple recovery accounting to the project-root resolver. Staging at `STAGING_ROOT` is separate transient data; it is neither persistent quota content nor the recovery store.

Use the existing per-copy `storage_resource_references` rows as the durable recovery manifest instead of adding a duplicate recovery table. Each recovery-file reference carries authenticated `owner_id`, original `project_id` (no project FK), a fixed internal `root_key` such as `recovery-v1`, a validated `relative_key` under the configured recovery root, a stable resource/copy key that includes run identity, verified byte count, and content hash. `recovery-v1` resolves only to the process's trusted `RECOVERY_ROOT` configuration; it is not a caller path and is not a `storage_root_mappings` project root. Write each copy through the existing durable filesystem reservation before backup I/O, then settle to the reference after verification. Retain the reference and charge after project-row deletion until recovery purge is verified. During removal quarantine, a pending job maps the logical `run-<UUID>/...` reference to either its original path or `.removed-run-<UUID>/...`; reconcile against that job-controlled pair and never mistake a missing original path during quarantine for zero usage.

Extend `project_removal_jobs` with explicit `owner_id` and the project's `storage_root_key`, alongside the existing `project_id` and UUID-only `run_ids` array. Keep the existing no-project-FK property so the intent survives cascading project/run deletion; prevent owner deletion while the job or charged references remain. Do not encode owner/root objects into `run_ids`. The project root key links the job to the retained project-root mapping; recovery references use the separate fixed recovery root key. The run IDs remain database-captured UUIDs and are the only names the cleaner may join beneath `RECOVERY_ROOT`.

The durable job row is also the removal barrier. Commit it before filesystem quarantine; while it exists, project writes, run starts, and file reservations for that project must fail closed. Then quarantine outside any PostgreSQL transaction. In a short follow-up transaction, recheck the job/owner/root, transfer the project mapping to retained, and delete the project. If the project still exists after a crash or failed commit, startup cleanup restores the quarantined run directories and removes the job only after restoration succeeds. If the project is gone, cleanup purges them, releases only the recovery references actually verified absent, and removes the job only after settlement succeeds. This preserves restart recovery without holding user/project/account locks over filesystem I/O. An ambiguous filesystem outcome keeps the job and byte charges pending.

For backfill, derive active recovery references from persisted change-set checkpoint references joined to their run/project/owner records and verify each file under `RECOVERY_ROOT` before making accounting ready. A leftover backup directory whose owner/run relationship was already cascaded away cannot be safely attributed from its filename alone. Keep the affected account unavailable until an operator-controlled inventory establishes ownership; do not assign it based on path guessing or count it as zero. This decision describes required schema and lifecycle behavior only; no migration, implementation, test, or deployment evidence is claimed.

## Startup reconciliation boundary (2026-10-19)

The storage migration initializes all `storage_account_totals` rows as `reconciling`. The current `createApplication` constructs quota repositories early but has no production scanner/reconciler call and invokes `readiness.markReady()` immediately after project-removal cleanup. Until a complete reconciler is wired before that readiness transition, positive relational writes and file reservations correctly remain closed because both check for `accounting_state='ready'`.

Smallest safe caller sequence:

1. After migrations and DB initialization, recover interrupted AI/Home operations and finish `project_removal_jobs` cleanup before taking the storage snapshot; removal cleanup may restore/purge recovery trees and release references. Construct the persisted root resolver and scanner from `config.workspaceRoot`, optional managed-root config, and `config.recoveryRoot`; do not require a new process/service.
2. Enumerate all existing owners, including owners represented by projects, root mappings, storage refs, or reservations. For each owner, commit `accounting_state='reconciling'` (or the existing fail-closed `unavailable` state) under the account_limits lock before any filesystem scan. This makes later DB content writes and new file reservations fail closed. Do not hold a QueryRunner, account lock, or project lock through filesystem I/O.
3. Resolve existing `pending` and `unknown` filesystem reservations before taking the canonical scan snapshot. Use each durable descriptor to inspect every affected project/recovery location through the trusted resolver; verify regular-file type, size, and hash, and account for operation claim/temp files as well as target/backup paths. Settle only an exact, fully observed outcome within reserved growth; release only when every prior target state is verified and no persistent side effect remains. If the descriptor does not cover a side effect, a root is unsafe/unreadable, or the outcome is ambiguous, keep the reservation and its reserved bytes, mark that owner unavailable, and do not proceed to reference replacement or ready. Never release by age.
4. Only after all unresolved reservations for an owner are terminal and `reserved_bytes=0`, scan canonical PostgreSQL content and every attached/retained project root. Resolve a path solely from persisted owner, locator project UUID, storage kind, and relative root; `root_key` is never a path. Scan the configured recovery root from owner/project/run checkpoint, storage-reference, reservation, and removal-job manifests, accounting for either original or quarantined `run-UUID` location while a durable removal job exists. Every physical recovery directory must map to a trusted owner/project/run identity; an unowned directory, missing configured recovery root, or unsafe path is not empty data. If ownership cannot be established, block storage reconciliation rather than guessing an owner.
5. Pass the complete measured reference set to `reconcileReferences`. Its final transaction must acquire account_limits, recheck no `pending`/`unknown` reservation and zero reserved bytes, replace references and set used bytes/state `ready` atomically. The current adapter already performs these final checks and transaction; preserve them. A new account with no persistent content, roots, recovery entries, or reservations has a complete empty scan and can become ready immediately.

The current reservation schema has only `pending|unknown|settled|released`; it does not distinguish a live filesystem executor from a crashed operation. Therefore automatic resolution of a pending row is safe only when the storage writer is quiescent (startup before this process accepts requests and no older writer can still be performing I/O). A runtime/worker repair must first close admissions and drain live operations; if it cannot prove quiescence, it must leave the owner unavailable rather than inspect and race an active writer. Existing `reconcileReferences` correctly rejects unresolved reservations, but that final guard alone is insufficient: settling a reservation during an earlier filesystem scan can make its references/counter change after the scan snapshot, then be overwritten by reference replacement. Resolve first, scan second, finalize last.

Keep the startup pass bounded so normal empty/new accounts become ready without waiting for manual repair. Later retries can use the planned worker from the existing backend codebase; do not add a new service. An owner with a genuinely unknown/unmeasurable outcome remains unavailable after bounded retries, with its reservation charged, until an operator can verify the filesystem and perform a supported settlement/reconciliation. If the global recovery root contains an orphan whose owner cannot be determined, do not mark accounts ready based on assigning that data nowhere; keep storage reconciliation blocked pending trusted inventory. This is the fail-closed exception, not a zero-byte result. These are source-based conditions for implementation; no startup reconciliation, concurrent-writer guarantee, or deployment behavior is claimed here.

## Managed-root orphan inventory decision (2026-10-19)

The startup reconciler currently resolves and scans only roots supplied by `storage_root_mappings`. That is incomplete for the first storage backfill: migration 0030 backfills projects that still have rows, while a completed pre-migration removal may have left its managed directory on disk after the project row disappeared. On a verified managed mount, startup must inventory the fixed namespace as well as mapped roots before any owner can become ready. The existing trusted layout is exactly `/account-workspaces/<owner UUID>/projects/<project UUID>`; this decision adds no storage service or mount.

First verify the configured managed root and its identity marker with `WorkspaceBoundaryAdapter` (including canonical `/account-workspaces`, no reparse point, and physical separation from `/workspace`). Enumerate with `lstat` at each directory boundary and never follow a symlink/reparse point. Accept only the marker plus canonical UUID owner directories at the managed-root level; beneath an owner allow only `projects`; beneath `projects` allow only canonical UUID directories. The project contents are then scanned with the existing regular-file/hash scanner. Empty UUID project directories are still roots and must not be silently dropped. Do not infer the physical host bind source from the marker: actual source/mount verification remains the operator's Task 8.1 check.

For each observed project UUID directory, compare its exact `(owner UUID, project UUID)` with current project rows and all persisted mappings. Existing matching active/retained mappings are scanned once. If there is no mapping and no project row with that UUID, but the owner UUID resolves to a current user and there is no mapping conflict for that locator, the deterministic server-owned path is sufficient to recover the historical managed root as retained content. Before scanning it, persist a retained mapping with `project_id=NULL`, `locator_project_id=<directory UUID>`, `storage_kind='managed'`, `relative_root='projects/<directory UUID>'`, and `root_key=projectRootOverlapKey(relative_root)`. The current 0030 insert guard only permits an active mapping tied to a project row; it must be narrowly extended for this internal, post-validation retained-root registration. This does not make a filesystem path an API input: `root_key` remains the existing path-shaped overlap/equality/reference key only and must never be parsed, joined, dereferenced, or exposed. Resolve the absolute root only from persisted owner UUID, locator UUID, storage kind and exact relative root through the existing workspace boundary. A project row present without its matching mapping, or any row/mapping for the same UUID that conflicts in owner, root kind or locator, is an integrity conflict; keep the affected owner unavailable rather than adopting it as an orphan.

Failure scope follows the namespace boundary. A malformed child, unexpected entry, mapping conflict, missing/unreadable path, or reparse point under a known owner's UUID directory makes that owner unavailable. A malformed top-level entry or UUID owner directory with no corresponding `users` row cannot be assigned to a live account; it is a global inventory failure, so startup must leave all account storage unavailable and must not let a later account become ready until an operator resolves the orphan and reconciliation succeeds. Never follow or count data through aliases, and never treat an unenumerated/unmounted namespace as empty. If managed storage is intentionally unconfigured, startup may omit the managed walk only when the database has no managed mappings, reservations, or managed references; evidence of managed use with no verified root keeps the affected owners unavailable. A configured but missing/wrong-marker root is unavailable, not an empty managed namespace.

This is a source-based inventory and fail-closed decision, not evidence that startup enumeration, orphan registration, physical mount verification, or rollout behavior has been implemented or tested.

## Process-visible free-space observation hook (2026-10-19)

Task 3.2 needs an app-side observation hook, while logical account quota remains separate from physical free space. The smallest existing-stack option is to sample the filesystem containing the trusted container targets `/workspace`, `/account-workspaces` when managed storage is enabled, and the configured `RECOVERY_ROOT`. Use the existing `startPeriodicMaintenance` lifecycle: one sample during startup and periodic samples on the existing maintenance cadence; do not add a worker/service or route. Do not include PostgreSQL because it is a separate container and the app cannot observe its backing volume.

The pinned app image is Node `22.20.0`; its `fs.promises.statfs(path, { bigint: true })` can report process-visible availability as `bavail * bsize` bytes (`bavail` is blocks available to unprivileged users). Format values as decimal integer strings. This is free space for the filesystem containing that container path; it does not identify a host bind source or prove host physical capacity. If multiple targets share one filesystem, their readings may repeat and must never be summed. Primary reference: [Node.js v22 file system documentation](https://nodejs.org/download/release/latest-jod/docs/api/fs.html), `fs.statfs` and `statfs.bavail`.

Define one optional `STORAGE_DISK_WARNING_FREE_BYTES` setting as a positive base-10 integer byte threshold, applied independently to each observed target. Do not invent a default or derive it from the 5 GB logical account quota. With a threshold configured, emit a structured warning when a target's available bytes become strictly less than the threshold; rate-limit by emitting only on transition into low state, and emit an internal recovery event when it returns above threshold. A statfs/target observation failure emits one warning on entering unavailable state and a recovery event after a successful sample; never report the failure as zero bytes. If the threshold is absent, there is no low-space alert; Task 8.1 must configure and validate an operational threshold/alert path for deployment.

Use existing `WorkspaceBoundaryAdapter` validation for workspace targets and the established server configuration/containment checks for recovery. A disabled managed target is skipped; a configured but missing, mismarked, unsafe, or unreadable target is an unavailable observation, never a reason to stat its parent/root filesystem as fallback.
