# Self-Review: Task 5.3 Direct Task Editor

- The route opens with a controlled form and keeps Save disabled when trimmed text, optional values, metadata, and the ordered checklist normalize to the loaded task.
- Save uses the editor baseline version and retains its idempotency key while retrying an uncertain outcome. Editing any field creates a new intent. Failure leaves the full draft visible.
- Conflicts keep submission blocked until the user reviews both snapshots and explicitly reloads or keeps the draft. Keeping a draft adopts only untouched fields from the reviewed latest version; a separate Save is required.
- Route changes and history transitions are guarded while dirty, saving, or deleting; pending delete transitions are reset so the task page remains active. Native `beforeunload` is conditional on those same pending states. Sign-out is denied by the existing preflight while DELETE is unresolved and otherwise awaits the explicit dirty-draft choice before session clearing. No task draft is persisted across account identities.
- Delete remains a separate destructive confirmation and uses the Task 4.3 delete operation. Its confirmation names the task, explains that a dirty draft is discarded, and says “Deleting…” while the request is pending. A late response only updates or redirects while the original task route remains active; failure preserves the draft and retry intent.
- Accessibility review found the original DOM tab order skipped Task title after heading focus. The route order now places the editor before task actions and return navigation; the production-browser run verified heading → Tab → Task title.
- Focused component tests cover validation/no-op behavior, checklist order/completion, conflict snapshots and rebase, uncertain save retry, route and hard-exit protection, sign-out cancellation, dirty-delete copy, and deferred DELETE success/failure/late-response cases.
- No material API or backend risk was introduced. Browser evidence uses mock API responses and does not claim backend integration.
