# Task 4.1 architecture preflight: stored policy and approval retirement

**Status:** Source-based architecture decision for the Task 4.1 contract. This is not an implementation, migration, runtime, provider, or deployment verification. Application code and tests were not changed or run.

## Decision

Use one durable `assistant_scope_policies` row for each owner and exact execution scope. The key is `(owner_id, scope_kind, project_id)`: Home uses `scope_kind='home'` with no project; a workspace uses `scope_kind='project'` and the project belonging to that same owner. The row stores the exact configured provider/model pair or two nulls, closed context-category and tool-capability enums, enabled/revoked state, a monotonic revision, and timestamps. It must not contain a JSON policy language, wildcard, arbitrary destination, caller path, prompt, secret, or external endpoint.

The policy sets are fixed, bounded application enums. They may authorize only context categories and handlers already implemented for that scope. A code change cannot silently widen a persisted policy: new capability values require an explicit policy revision/backfill. Project file/fact/message selection and exclusions remain authoritative in `project_chat_contexts`; the policy row bounds the categories, while the context row names the selected content. Exclusions take precedence over every inclusion source.

Backfill rows only for scopes whose owner relationship is established by current persistence. Create rows for new accounts and projects in their trusted provisioning transaction/path; do not create them as a side effect of policy GET or an arbitrary run. A missing row is `policy_unavailable` and blocks dispatch. If a provider is not configured, store a null provider/model pair and report unavailable. A trusted configuration synchronizer may fill that pair only while the row is enabled and unrevoked, and must increment its revision. It cannot replace a non-null provider/model or revive a revoked row; later provider/model changes require an explicit trusted policy revision. Main owns the new migration and registration after Task 3.3 migration `1710000031000`; the main-assigned migration identifier must be used. No Task 3.3 callback is needed before the table exists.

Revocation is a sticky trusted/operator action: set `enabled=false`, set `revoked_at`, and increment `revision`. It blocks the next provider/tool dispatch and durable write after the revocation commits. A guard that passes first admits only that one already-started external operation; it does not prove the ability to recall it atomically. Recheck principal and current policy before every later dispatch and before durable output/promotion. No user-facing policy editor or revoke control is assigned in Task 4.1. Existing project-context exclusions and account disable/expiry remain user-visible controls. Existing `provider_permissions` are exact project/provider/model `send_selected_context` history; they are not a Home grant, do not imply tool capabilities, and must not be promoted into this broader scope policy. The existing permission revoke UI/route must not be described as revoking the new policy.

For a Home turn, derive its owner and Home scope from the authenticated session and persisted conversation. If a tool targets a workspace, require the Home policy and the target project's policy, then intersect their closed capability sets. Derive the target project from an owner-checked database record; never accept an owner ID or arbitrary project/path authority from the model or browser. For direct workspace chat, require the exact owner/project policy plus the active project, persisted context selection, trusted Task 2.2 file root where file access is needed, and fixed handler/runtime allowlists.

Task 3.1 credit admission, Task 3.2 storage accounting, Task 2.2 root validation, and active-principal/expiry checks remain independent mandatory gates. A policy row cannot make a provider, sandbox, storage account, or egress path ready. The read-only effective-policy status route is descriptive, not an authorization token; every start/continuation/write checks live state again.

## Legacy approval transition

Apply one rule to every obsolete mutating decision route: consent decisions, proposal acceptance/execution, workspace provider-egress decisions, change-set decisions, and sandbox-command decisions return HTTP `409` with stable code `POLICY_ACTION_RETIRED`, for every decision value. The handler makes no state change and performs no provider send, runtime/tool continuation, or canonical mutation. Keep authenticated cancellation routes and owner-scoped GET/history/status reads. Keep old events and records as history, but never resume an old pending or approved record under a new policy. Render a safe blocked/unsupported legacy state and require a fresh request; cancellation remains available for old in-flight work.

This uniform rule is needed because several “deny/reject” variants still call a runtime: Home tool-result denial sends a tool result through `DecideHomeConsentUseCase`, and sandbox command rejection calls `agentRuntime.decideCommand` in `DecideSandboxCommandUseCase`. A branch that appears to reject permission can therefore continue an old runtime loop. Retiring all decision variants avoids a phase-dependent bypass. New automatic runs use current run/turn status, safe progress, and actual action receipts; they do not emit consent-allow or proposal-accepted claims.

## Implementation call-flow checkpoint (2026-10-19)

The current stable guard is `AssertAssistantExecutionPolicyUseCase` in `backend/src/modules/assistant-policy/use-cases/assert-assistant-execution-policy.ts`. `assertWorkspace({ ownerId, projectId, providerProfile, model, policyRevision? })` rechecks the active principal, owner-scoped active project, exact stored provider/model, enabled/revoked state, optional expected revision, and trusted runtime capability. `assertHome({ ownerId, projectId?, providerProfile, model, homePolicyRevision?, workspacePolicyRevision? })` does the same for Home and, when the persisted conversation targets a project, intersects Home and that exact workspace's capabilities. It returns the current revision(s) and effective closed capability set. It is a fail-closed policy/runtime capability gate, not proof that every provider send is metered; Task 3.1's real per-attempt admission remains mandatory. No DB lock should span provider or bridge I/O.

### Workspace run path

`SendChatMessageUseCase` currently creates a pending-approval run, optionally routes it through `DecideEgressUseCase.approveWithRememberedPermission`, then the client separately calls `/start`. New runs should instead bind the policy during creation and use a server-internal policy-authorized path. After resolving the owner-scoped project and persisted `project_chat_contexts`, `CreateAiRunUseCase` calls `assertWorkspace` and persists the returned `policy_revision` with the unchanged canonical manifest. The trusted prepare/start flow reuses current message/file/fact hash validation, quota-aware writes, staging, `beginStart` idempotency/cancellation fencing, and the real runtime's Task 3.1 admission. Recheck the expected policy revision immediately before provider start, every subsequent runtime/tool dispatch, automatic change application, and durable output. Do not call the legacy egress-decision route or `recordDecision(approve)`, and do not grant/use `provider_permissions` as authorization for the new path.

Migration `1710000032000` extends `ai_run_decision`, `change_set_decision`, and `sandbox_command_decision` with `policy_authorized` as the durable server-policy provenance. `ai_runs.policy_revision` must be non-null when its run decision is policy-authorized; command rows bind through their immutable `run_id` and include that run revision in the claim fingerprint. This provenance is distinct from historical user choices `approved` and `rejected`; never backfill or reinterpret old rows. Normalizers/OpenAPI must include policy-authorized output values, and run responses must omit `providerApprovalMode` for them. The start path must reject legacy runs without a policy revision even if their historical decision is `approved`. Down first guards against any policy-bound history or policy-authorized run/change-set/command rows, then rebuilds/casts all three enums to their original labels because PostgreSQL does not remove enum labels directly.

The supported workspace file-change path and the bounded read-only sandbox-command path use separate internal authorization records. Existing automatic file application retains manifest/hash/version checks and Task 3.2 quota/recovery boundaries. Sandbox commands must use the private policy-authorized path below; an unsupported command/runtime is blocked and the waiting runtime is stopped, never sent a legacy reject/deny response. Task 4.2 owns future direct typed Home task/workspace action expansion.

### Policy-authorized bounded sandbox command path

The current profile includes `bounded_sandbox_command`, so the implementation must support safe bounded commands without making them appear user-approved. The smallest persistent provenance is `sandbox_commands.decision='policy_authorized'`, stored with the existing decision idempotency key/fingerprint. Add that enum value to the still-WIP migration `1710000032000` alongside the assistant-scope and change-set values; do not add a migration or edit initial migration `1710000005000`. The application begins using the new label only after migration commit. Any same-migration predicate that must test the new label compares `decision::text` with the text literal. Down must refuse rollback while any run, change-set, or sandbox-command row has policy-authorized history, then rebuild all affected enums only when no such history remains.

No per-command revision column is required: every command is linked by `run_id` to an `ai_runs` row whose `policy_revision` is set at creation and is omitted from repository `save()` updates. The claim fingerprint must include owner, run, project, command ID, proposal hash, the linked immutable run policy revision, and the fixed command-policy version. The policy-authorized decision itself plus that run link/fingerprint are the audit source. Historical `approved` command rows remain human decisions and can never be claimed or restarted by this path.

Use the existing flow in `StartAiRunUseCase` and `ISandboxCommandRepository`, with a private executor method on the existing command use-case. On Hermes `tool.proposed`, parse and validate the proposal and persist the owner/run-scoped command row; `HermesAgentRuntime.proposeCommand` only binds the runtime permission to the row ID. At the following `approval.required` event, the private executor reloads the current run and command, verifies active principal/project and `run.decision='policy_authorized'` plus non-null `policyRevision`, calls `AssertAssistantExecutionPolicyUseCase.assertWorkspace` with that expected revision, and requires `bounded_sandbox_command` in the current capabilities. It also checks trusted runtime readiness and the exact fixed command profile before admission.

Do not reuse `normalizeHermesPermission` for automatic execution. It marks every raw Hermes terminal string `sensitive` and can assign `approved_registries` network access to package-install commands. The automatic subset must accept only a canonical shell-free token sequence which maps through the existing `SAFE_COMMANDS` and `COMMAND_LIMITS` (`network='denied'`): no shell metacharacters, quoting, escapes, variable or glob expansion, redirection, options, environment assignments, absolute/parent paths, secret/protected paths, or paths outside the exact per-run selected-file snapshot. Reject sensitive/registry-access commands and any proposal that cannot be normalized exactly; do not broaden the fixed command allowlist. The bridge's run copy must contain only the current manifest-selected files. If that copy or command restriction cannot be established by trusted runtime evidence, treat the runtime capability as unavailable.

Add a separate repository claim method rather than calling `recordDecision({decision:'approve'})`. Under the existing command row lock, it may transition only `pending/awaiting_approval` with `cancel_requested=false` to `policy_authorized/running`, recording a deterministic internal key and the bound fingerprint. The same lock/state predicate arbitrates the claim against `recordCancellation`: if cancellation commits first, do not dispatch; if the policy claim commits first, cancellation requests stop and the runtime result is discarded. A same-key/fingerprint replay returns the saved command without starting a second runtime execution; a mismatch conflicts. Preserve the public approve/reject input type and keep its controller at `409 POLICY_ACTION_RETIRED`.

Hermes continuation must be asynchronous because `HermesAgentRuntime.executeCommand()` sends the internal runtime permission and waits for `permission.result`, which `projectBridgeEvent()` reads from later events in the same `startRun()` iterator. Start the executor at `approval.required` as a tracked per-run promise and continue consuming the iterator; never await the poll from the event projection itself. Suppress `approval.required` from client events. Accept tool started/progress/completed events only for the matching claimed command. At the runtime terminal event, await all tracked command tasks before completing the run; a failed or unresolved task makes the command and run require review, never success. Catch every task rejection and persist a bounded safe status so no promise is unobserved.

Recheck principal, active project, exact run policy revision, and `bounded_sandbox_command` immediately before the runtime permission dispatch and again before persisting or publishing a command result. Do not hold database locks across bridge calls. A check that succeeds first admits that one already-started operation; revocation or expiry committed before a later guard prevents the next dispatch/output. If a guard fails while Hermes is waiting for permission, cancel the run and confirm shutdown rather than sending a synthetic negative tool result that could continue the model loop. Keep existing cancellation idempotency and ensure cancellation and policy claim serialize on the command row. When command outcome or runtime cancellation is unknown, persist `review_required` with no output preview and do not issue another command.

Keep all input/output boundaries explicit. Commands run only in the isolated per-run copy produced from the approved manifest, never against the host/project root. Before using the command result for further model inference or exposing it to a client, require trusted evidence that the pinned bridge enforces the fixed command allowlist, `COMMAND_LIMITS` wall/idle/process/memory/output bounds, and `network='denied'` inside the sandbox. The application-side `sanitizeCommandResult()` only redacts and bounds the persisted preview; `HermesAgentRuntime.executeCommand()` currently ignores its `limits` argument and its bridge probe attests the Hermes/provider/model/endpoint, not per-command limits. Therefore post-response truncation is not proof that the command output was bounded before entering the model context. Missing command-policy evidence is fail-closed. When evidence is present, retain output redaction, max 4 KiB persisted preview, bounded output bytes, and hash/result metadata; recheck policy before any result is shared or promoted.

Startup recovery must extend the existing `RecoverInterruptedAiRunsUseCase` path to mark command rows belonging to interrupted policy-authorized runs as `review_required` when their command status is `awaiting_approval`, `running`, or `cancel_requested`; this includes a pending row created before the policy claim. Do not store raw result output. The current run recovery marks active runs for review and never resumes them; command rows must receive the same treatment before the app accepts requests. If a process exits after proposal, claim, or runtime permission dispatch, the exact external outcome is unknown: do not reclaim, replay the idempotency key into the runtime, or infer success. Reuse the existing recovery use case/repository and fail startup if the run/command repair cannot be confirmed; no new worker or service is needed.

### Home turn revision binding and continuations

Migration `1710000032000` already adds nullable `home_policy_revision` and `workspace_policy_revision` to `home_turns`; they are internal binding fields, nullable for legacy turns. Extend `HomeTurn`, `HomeTurnRow`/`toHomeTurn`, and `SubmitHomeTurnInput` to carry these decimal revisions, and persist them in the existing `TypeOrmHomeConversationRepository.submitTurn` transaction with the turn/user message. `SubmitHomeTurnUseCase` loads the conversation by trusted owner, derives the optional workspace target from that persisted scope, calls `assertHome`, and binds the returned revision pair. A new automatic turn has no consent disclosure row; persist a durable starting/running marker before external `runtime.start` so retries never duplicate a possibly sent provider request. If readiness is unavailable before send, return a safe unsupported/no-send outcome; if transmission is uncertain, retain `unknown`. An idempotency replay returns the existing turn and original revisions without rebinding or restarting it.

`GetHomeTurnUseCase` must not poll a legacy turn with null policy revisions. Old pending consent turns stay history/blocked; old running turns are cancelled if possible and otherwise become unknown, never resumed. For a policy-bound running turn, reassert the stored Home/workspace revision pair before poll/projection, before each `home.tool.requested` is resolved, and before every `runtime.sendToolResult` continuation. Check the handler's exact capability against the returned intersection. If a policy/capability check fails or a tool cannot be safely handled, do not send a synthetic denied result: that bridge call may continue the model loop. Cancel if available and otherwise stop projection and record a safe blocked/unknown state. Reassert again before durable assistant output, event, or receipt writes.
