## Decisions

Task 7.1 is a backend change in the existing Clean Architecture modules. PostgreSQL owns schedules, occurrences, leases, fencing generations, and run links. A bounded worker uses the existing server/worker lifecycle and database claiming; the timer is only a trigger. Do not add a queue framework, runtime framework, policy authority, or external dependency. The frontend/FSD is outside Task 7.1; Task 7.3 owns schedule controls. DDD and Hexagonal Architecture are excluded.

Use the existing skills and Home execution workflow. Each schedule owns one durable Home conversation scoped to exactly one active, mutable workspace. It has one unique idempotency key per intended local-date occurrence; Run now creates its own durable occurrence/key. A schedule targeting several workspaces is represented as one schedule per selected workspace, each with its own conversation and results. Do not silently accept a workspace array, use a Home-wide conversation to read across all owner workspaces, or grant owner-wide mutable tools. `HomeConversationScope`, skill invocation, project-memory context, and Home tool authorization currently bind to one persisted conversation/workspace. A combined cross-workspace briefing would need a separate trusted multi-scope context contract and is outside this change.

Scheduled Daily briefing must remain read-only by capability: the delivered `daily-briefing` template declares only `home_task_read`; reject or skip any scheduled revision whose declared tools include a write capability. Current persisted Home policy still applies and can further narrow the declared capability. A workspace-bound skill must match the schedule workspace; an account-wide skill may run in that workspace conversation. Record the exact current skill revision/version used for the occurrence and fail closed if it changes or is disabled.

The existing backend already validates IANA zones and resolves DST day boundaries with native `Intl` in `credits/domain/credit-time-windows.ts`; no timezone package is justified. Build the small schedule-local-time resolver on the installed Node `Intl` behavior and prove the plan's gap/fold rules with fixtures. Context7 was not callable in this session; if implementation needs additional vendor-specific behavior or a new library, the developer must record the required documentation evidence or its unavailability in the task evidence.

## Occurrence and dispatch protocol

Keep the smallest scheduler boundary in `modules/automations/{controllers,dto,use-cases,domain,repositories}` with a TypeORM adapter and the existing composition root/worker lifecycle. Use additive PostgreSQL schema after the active Task 3.6 migration is finalized; do not edit delivered migrations or assume the next migration number. The developer-owned contract decides exact DTOs and schema names. Persist, at minimum, the schedule owner/workspace/conversation/skill IDs, local time and canonical IANA timezone, enabled state and revision, next UTC due instant, and occurrence intended instant, status, schedule revision, claim token/generation/expiry/heartbeat, stable request-key digest, linked skill invocation/Home turn, attempt count, and safe failure code. Enforce unique `(schedule_id, intended_for_utc)` and index bounded due/lease recovery queries.

1. Claim bounded due occurrences transactionally with `FOR UPDATE SKIP LOCKED`; increase a fencing generation and set a database-clock lease. Heartbeats and all later writes require the current token, generation, and unexpired lease. Claiming does not hold locks across Home, provider, or filesystem calls.
2. Before dispatch, in a short transaction, re-read and fence current owner activity/expiry and demo cleanup generation, active owned workspace, schedule revision/state, occurrence lease, and current skill revision/enabled/read-only declaration. Require an enabled schedule for automatic occurrences. Run now is a distinct user-authorized occurrence and may run while paused only if the schedule is still active and its revision has not changed. Commit the `dispatching` marker before invoking Home, then release locks.
3. Pass a trusted scheduler guard through `InvokeSkillUseCase` into `SubmitHomeTurnUseCase`; repeat the schedule/owner/workspace/skill/expiry check at the existing final pre-send boundary. Existing Home policy, provider readiness, current credit admission, storage quota, context snapshot, and tool capability checks remain mandatory.
4. Persist the occurrence-to-invocation/turn link as soon as the Home submission returns. Derive the occurrence state from the persisted Home turn: a runtime `accepted` result remains `running`; completed/partial, failed/unsupported, and confirmed cancelled are terminal. Poll/reconcile the existing turn through `GetHomeTurnUseCase`; do not build a second inference or message persistence path.
5. Fence final assistant-message/result commit on the same current schedule revision, claim generation, active owner and expiry, current skill revision, and bound context revisions. The result remains in the Home conversation; occurrence metadata stores its reference and status, not a second narrative copy.

If a persisted turn is running, cancelled-requested, or unknown after worker loss/restart, treat the external inference outcome as potentially sent. Reuse its stable Home turn and request key; never call `runtime.start` again for that occurrence. Persist `interrupted_unknown` until the existing runtime/credit reconciliation path can establish a safe terminal outcome. Retry only work proven not sent by the existing Home/runtime path, with a bounded attempt count and a new attempt key; a timeout, expired lease, or missing worker memory is not proof of no send. Unknown billing remains under the existing credit reservation/usage rules and is never released as free work.

Compute each occurrence from its local calendar date and stored IANA zone. For a nonexistent local time choose the next valid instant; for a repeated time choose the earlier instant and create one occurrence. On downtime, create at most one most-recent catch-up, coalesce older days, then persist the next future UTC instant. Use the database clock for leases and UTC occurrence identity.

## Deletion, expiry, and lock boundaries

Pause, disable, schedule deletion, workspace removal, and demo expiry first persist the new schedule revision and cancellation intent. Mark not-yet-dispatched occurrences cancelled. For a linked active Home turn, persist cancellation through the existing `CancelHomeTurnUseCase`, then signal the runtime outside the transaction. Confirmed cancellation is terminal; cancellation timeout, unknown provider state, or unresolved billing remains a durable blocker. A lease expiry alone never clears it.

Before demo owner purge or workspace/Home cascade, the cleanup path must inspect exact schedule/occurrence/turn IDs, cancel active work, and prove all linked turns and occurrences are terminal. Pending, dispatching, running, cancel-requested, or interrupted-unknown work blocks purge. Once safe, normal Task 3.5 owner cleanup and migration 0027 workspace deletion may remove the schedule conversations, turns, invocation metadata, and schedule content. Do not retain deleted Home histories, rewrite Task 3.5's settled financial ledgers, delete shared credit totals, or detach in-flight/unknown reservations. If an external result cannot be resolved, keep cleanup pending and surface a safe operational state; do not fake success or purge it.

Keep the established demo lock order and extend it only with scheduler rows after the owner lock and before dependent copy/finalization rows. Scheduler claim transactions lock occurrence rows only and do not then acquire owner/schedule locks. Other multi-row schedule checks use a consistent owner → schedule → occurrence order. No scheduler/cleanup transaction acquires `credit_runtime_policy`; existing provider admission continues to take policy first. Never hold a DB lock while cancelling, polling, or starting runtime work.

## Focused proof required

- Two independent workers claim the same due time: only one current fence can dispatch or commit. A stale heartbeat, dispatcher, and final result commit are rejected after lease takeover, pause, schedule revision change, skill edit/disable, workspace removal, owner disable, or demo expiry.
- Restart after claim-before-dispatch, after Home turn persistence, after provider acceptance, and during polling. Reuse of the occurrence key must not create a second turn/runtime start; ambiguous persisted turns become interrupted-unknown and retain conservative credit state.
- DST gap/fold fixtures and downtime catch-up coalescing produce one intended occurrence and a future next-due instant.
- Daily briefing can read only through its declared read capability and current Home policy; attempts to call task/workspace writes are denied. Foreign workspace, unselected workspace, disabled workspace, disabled skill, changed skill revision, stale context, expired owner, and paused automatic schedule do not dispatch or persist output.
- Expiry and workspace deletion cancel and wait on linked Home turns/schedule jobs. Unknown cancellation/runtime/credit state blocks cascade; confirmed terminal state permits ordinary purge. Settled credit reservation/usage detail and shared daily/campaign totals remain exactly as Task 3.5 specifies.

This is a source-based preflight only. No schedule implementation, migration, live runtime, two-worker race, restart, PostgreSQL, or test proof is claimed.

## Worker lifecycle ruling

The release architecture's backend startup rule is explicit: reuse `composition-root.ts` or a small shared factory, and keep worker startup separate from HTTP server startup. The Task 7.1 contract likewise requires an independent worker entrypoint. Current `createApplication()` starts both the general application maintenance loop and the `AutomationWorker` loop; because `server.ts` calls it, the HTTP process currently starts automation as a side effect. The older phrase above, “existing server/worker lifecycle,” does not waive that requirement.

Keep one composition root and introduce an explicit API-versus-automation-worker lifecycle. API mode starts only the existing storage, project, and demo maintenance and serves the existing schedule/occurrence APIs; it does not start `AutomationWorker`. A small worker-only entrypoint uses the shared composition wiring in automation-worker mode, starts only the existing bounded `AutomationWorker.runOnce()` periodic trigger, and never opens an HTTP listener. It shares the same runtime and Home execution path; each process creates one normal dependency graph from the same configuration. Do not add a second runtime, queue, or orchestration framework, and do not add an API endpoint that starts or polls the worker.

The worker entrypoint owns SIGINT/SIGTERM shutdown: stop the periodic handle and await its in-flight pass, then close its database and provider resources. Composition or startup failure must stop any started handle and destroy an initialized data source. The HTTP server remains responsible for closing its listener, stopping API-mode maintenance, and closing its own resources. Multiple worker processes remain safe through the existing PostgreSQL claim/lease/fencing protocol.

Add only focused lifecycle proof: API mode does not start the scheduler loop; worker mode starts the loop without an HTTP listener or API maintenance; stop drains the active pass and closes resources; initialization failure cleans up. Typecheck/build the worker entrypoint. Reuse the existing scheduler integration result (4/4), fresh-child restart proof, cleanup unit result (11/11), and filtered cleanup PostgreSQL result (1 pass, 3 expected skips; fresh guard clean); this bootstrap-only correction does not justify a new PostgreSQL matrix. The source-based status above describes this preflight's own work. The lifecycle separation is implemented and verified by the focused checks and worker build recorded in `artifacts/worker-lifecycle.md`.
