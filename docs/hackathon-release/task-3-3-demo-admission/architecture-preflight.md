# Task 3.3 Private Demo Admission — Architecture Preflight

Date: 2026-10-19
Status: Source-based implementation input for Task 3.3. No application code, database test, provider call, or deployment was changed or verified here.

## Scope and source baseline

This preflight covers admission, session resumption, abuse counters, and the identity/storage readiness needed before a new demo can receive a session. Task 3.4 owns copying the protected showcase into the demo account; Task 3.5 owns durable expiry cleanup. This document defines their integration boundary but does not implement either task. The release remains a modular monolith: keep HTTP handling in a focused demo-admission controller, policy in use cases, persistence behind repositories, and TypeORM details in infrastructure. Frontend changes are outside this slice; DDD and Hexagonal Architecture are not needed.

The release architecture already defines a fixed 24-hour demo lifetime, same-origin admission, private passwordless identities, persistent limits, and a spending pause that must not block read-only exploration. No architecture.md change is needed. The implementation baseline is:

- `Personal-AI-Workspace/backend/src/modules/auth/controllers/request-auth.ts` enforces exact `APP_ORIGIN`, derives CSRF tokens from the opaque session token, and defines `__Host-pa_session`.
- `backend/src/modules/auth/controllers/auth-router.ts` sets HttpOnly, SameSite=Lax, path `/` cookies, and uses the configured secure-cookie flag. `backend/src/infrastructure/auth/opaque-token-provider.ts` generates 32-byte random tokens and stores only a keyed digest.
- `backend/src/modules/auth/use-cases/get-session.ts` validates session revocation and both session/account expiry. The generic `SESSION_TTL_HOURS` currently defaults to 12 hours, so demo lifetime needs its own setting.
- `backend/src/infrastructure/config/app-config.ts` currently has no demo admission or trusted-proxy settings. `backend/src/app.ts` does not enable Express proxy trust, so its default is direct-socket IP handling.
- `1710000026000-add-account-identity.ts` supports passwordless demo users with a required account expiry. `1710000028000-create-credit-ledger.ts` creates the shared `account_limits` row and defaults global inference to paused with demo daily/campaign budgets unset.
- Task 3.2's `TypeOrmStorageQuotaRepository.reconcileReferences()` can mark an owner ready only after checking for unresolved reservations and setting measured references. `StorageQuotaStartupReconciler` only scans owners at startup; it does not automatically make a user created later storage-ready.

## Admission and session decisions

Use one same-origin `POST /api/v1/demo/session` create/resume operation with an empty strict request body. The client cannot select an owner, expiry, credit balance, or path. Always run the exact `sameOrigin(APP_ORIGIN)` check. If a cookie resolves to an active regular account, return a conflict and preserve that cookie; never silently replace it. A valid demo cookie returns the same principal and expiry. It does not create another user/session, increment admission counters, or extend the expiry. Invalid/expired demo cookies may be cleared as the replacement response is prepared.

Use the existing opaque token format and cookie settings. Set cookie expiry equal to the persisted session/account expiry. Configure a separate `DEMO_SESSION_TTL_HOURS`, default `24`, accepted only in the range `1..24`; the value is fixed for each new admission and is never refreshed. In the creating transaction, take `created_at` from PostgreSQL `clock_timestamp()` and set `users.expires_at` and `sessions.expires_at` to that timestamp plus the configured TTL. This avoids request-clock drift and keeps account and cookie expiry aligned. Production must keep the `__Host-` cookie Secure; local insecure HTTP remains governed by the existing explicit development setting.

For authenticated POSTs, also require the existing session CSRF token (`X-CSRF-Token`); for the initial anonymous POST there is no CSRF token yet, so exact Origin validation and the SameSite cookie policy apply. Do not reuse `authenticateRequest` blindly if its invalid-cookie handler would erase a valid regular session: the admission use case must resolve the presented session first and preserve regular-session state on conflict.

Deduplicate concurrent client retries with a high-entropy `Idempotency-Key`. Persist only its digest with the network identity and provisioning row; never log the header. The key makes a single request create at most one admission/principal. It is not a session credential: without a valid demo cookie it may return only generic persisted status (or a generic terminal failure) and may not issue or recover a cookie. Replaying a pending key does not resume bootstrap. If a response is lost before the browser receives its cookie, that request key cannot recover the session; a new admission is allowed only through the persistent network/global limits. This avoids turning an idempotency header into a bearer credential. Repeated requests that do have the valid demo cookie resume the same persisted session.

Persist a small `demo_admissions`/provisioning record uniquely keyed by a globally unique `request_key_digest`, with a nullable `owner_id` until the principal is created, then `pending | ready | failed`, immutable `created_at`/`expires_at`, and bounded failure code. The original network key may be retained as rate-limit metadata, but it is not part of the idempotency key. This ensures an IP change or network-key rotation cannot create a second owner for the same retry key. The digest is not a session credential; raw IP, raw request key, exception text, and secrets are never stored. The principal remains passwordless and has no login identifier. A failure or uncertain storage bootstrap cannot issue a cookie; replay returns only generic persisted status or failure and does not retry provisioning. Mark `ready` and insert the first session in one short transaction after prerequisites complete. A failed response must not reset credit use or campaign counters.

## Persistent limits, proxy trust, and privacy

Add PostgreSQL fixed-window counters rather than reusing `InMemoryLoginRateLimiter`, which is process-local and login-specific. Keep three separate scopes: global new-admission attempts, network new admissions, and AI-run starts per stable demo `owner_id`. Store integer counts, window boundaries, and configured counter kind; use atomic upserts/row locks in one transaction. Never key session limits by the raw cookie or session row, because token rotation would reset them. Run pruning on the same bounded retention horizon as the maximum configured window. A configured global attempt cap also bounds the creation rate/cardinality of per-network buckets; reject before inserting a new network bucket once that global cap is exhausted. Counter thresholds and windows are operator configuration inputs, not credit allowances. Do not invent numeric spending defaults; if required abuse-limit config is absent or invalid, fail closed for new anonymous admissions while allowing valid existing demo sessions to resume.

Derive the network key from `request.ip` only after proxy trust is configured. Add optional `TRUSTED_PROXY_CIDRS` and pass only the validated CIDR list to Express `trust proxy`; omit the setting to retain Express's default `false`, which uses the direct socket and ignores forwarded addresses. Never set trust to `true` or a hop count. The app must not parse `X-Forwarded-For` itself. A deployment with an unconfigured reverse proxy will bucket all visitors under that proxy address; document the shared-network effect rather than trusting arbitrary forwarding.

Do not persist or log raw IPs. Require a separate operator-supplied `DEMO_NETWORK_HASH_SECRET` with at least 32 random bytes; do not invent a value or reuse `SESSION_SECRET`. Store `HMAC-SHA-256(secret, "demo-network:v1:" + request.ip)` and a derived key identifier, never the secret. Treat those hashes as sensitive pseudonymous operational data and delete counter rows after their windows expire. When the secret changes, deny new admissions while any live network window has a different key identifier; resume admission only after those windows expire and are pruned. This preserves the old rate history without storing raw IPs or silently resetting counters. Missing/invalid secret has the same fail-closed behavior for new admissions, not for valid session resumption. Do not bind an existing valid session to its current IP; shared NAT users share a bucket, and changing IP can consume another bucket. No browser fingerprinting is added.

Per-session AI-run start rate counting is abuse control only. It is separate from Task 3.1 credit units, reservations, settlement, and `demo_max_concurrent_calls`. Count at the run-admission boundary by owner ID in a short transaction, then invoke the existing credit admission path; do not hold the rate counter transaction while acquiring credit locks or performing provider work. A cookie reset cannot reset either the account ledger or global demo budgets. Do not add a second credit balance or require AI budget configuration to create a session.

## Storage readiness, locks, and retry behavior

Create the demo user, admission row, and `account_limits` row in one PostgreSQL transaction, using a generated server-side UUID and the existing demo identity constraints. Do not seed a credit allowance or add a parallel balance; the existing credit adapter initializes a zero-use counter when an enabled credit admission first needs it. Before issuing a session, initialize storage for this known-empty new owner through a narrow bootstrap port backed by `TypeOrmStorageQuotaRepository.reconcileReferences(ownerId, [])`. Call it only after establishing that no project/root, content reference, file reservation, or recovery entry exists for that new owner. This is a complete empty scan, not a shortcut for existing accounts. On failure, leave the account pending/unavailable and issue no session.

Use short transactions and the existing `account_limits` lock anchor. For an anonymous create, lock in one order: global admission window, globally unique request-key/admission row, network window, then new user and `account_limits`. Insert/lock the admission row before counting, then check its state under the same serialization; same-key races do not double-count or create duplicate owners. A cross-network replay of a known key may read only generic status and may never receive a cookie without a valid demo session. Commit the new owner in `pending` before storage bootstrap. Storage reconciliation runs after the creation transaction commits and outside its locks. In the final transaction, lock the admission row, make only the first `pending -> ready` transition, and insert one session with that transition; a no-cookie retry after readiness can observe status but cannot mint another session. No database lock, QueryRunner, or account lock spans filesystem or provisioning work. Replays are status-only: pending returns `202`, ready returns generic `200` status, and failed returns a generic failure. They never resume bootstrap or issue a cookie. Task 3.5 must durably clean expired pending/failed admissions and their owned data without selecting regular users or protected showcase data.

Do not lock `credit_runtime_policy` for a session-only action. Use the established credit repository when an AI run is requested. Its safe defaults (`inference_paused=true`, demo daily/campaign limits unset) must continue to reject AI calls until the operator configures budgets and Task 3.1's provider bounds. Demo session creation and bounded read-only/non-AI exploration remain available while AI is paused. UI/API state should report AI unavailable without blocking reads; no provider call or default credit spend is part of admission.

Task 3.3 should expose a narrow `IDemoContentProvisioner`/workspace-readiness port keyed by admission/owner ID. It must not accept caller paths or expose showcase identifiers. Task 3.4 owns the implementation that copies a versioned protected snapshot using the Task 2.2 managed root, stages idempotently, and keeps workspace entry unavailable until DB rows and files agree. The current Task 3.3 `ready` state means identity, session, and empty-account storage prerequisites are ready; Task 3.4 must add the copy-ready gate before presenting an editable workspace. Task 3.5 owns durable expiry cleanup and retryable removal manifests.

The developer contract should cover PostgreSQL concurrency for duplicate request keys and same-network admission, valid demo resume without expiry extension, regular-account conflict preserving the cookie, cookie clearing subject to persisted network counters, IP spoofing from an untrusted peer, trusted CIDR proxy-chain behavior, missing/rotated network key fail-closed behavior, storage-readiness failure without cookie issuance, and zero-balance/AI-paused non-AI admission. Verify that counters remain bounded/pruned, request cookies and idempotency values never appear in logs, and a token rotation leaves account/global credit rows unchanged. Do not claim shared Wi-Fi gives a unique visitor identity or that admission limits eliminate anonymous abuse.

Primary external reference: [Express 5 application API — `trust proxy`](https://expressjs.com/en/5x/api/application/) (official docs, consulted 2026-10-19). It states the default is disabled and warns that forwarded headers can be spoofed; its CIDR trust option derives the client as the nearest untrusted address. No new dependency is required.
