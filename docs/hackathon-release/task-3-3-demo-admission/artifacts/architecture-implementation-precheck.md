# Task 3.3 source implementation precheck

## Scope and status

Read-only review of the current Task 3.3 admission, repository, storage-bootstrap, HTTP, and run-start wiring. No app files were changed; no tests, PostgreSQL checks, deployment checks, or provider calls were run. This is an implementation risk note, not a QA verdict.

## Decisions and current source

- **Idempotency and cookie authority are sound in the inspected path.** `CreateDemoSessionUseCase.execute` returns only the stored generic state for a known digest before it derives network identity (`backend/src/modules/demo/use-cases/create-demo-session.ts:22-25`); a concurrent duplicate is also status-only after `beginAdmission` (`:40-46`). The router writes the session cookie only for `kind: 'created'` (`backend/src/modules/demo/controllers/demo-admission-router.ts:81-96`). The repository globally serializes creation and locks/rechecks the digest before creating the user (`backend/src/infrastructure/database/repositories/typeorm-demo-admission-repository.ts:86-100`); `completeWithSession` atomically inserts the session and changes pending to ready (`:203-244`). Thus cross-network replay cannot create another owner or obtain a cookie. A lost response/cookie is intentionally unrecoverable by key; the user remains inaccessible and cleanup is the recovery path.
- **Pending recovery is cleanup-only in this slice.** The current create use case retries storage bootstrap at most three times only in the original request (`create-demo-session.ts:48-62`). Replaying a pending or ready key does not resume work or issue a session; failed state is also terminal for that key. This is the right non-bearer behavior. Task 3.5 now explicitly assigns durable, restartable cleanup of expired pending and failed owners (`tasks.md:331`). Keep this dependency explicit and do not describe same-key bootstrap as retryable. The current preflight still contains the contradictory phrase "A pending row must be retryable on the same request key and owner" (`architecture-preflight.md:45`); correct that wording to "status-only replay; Task 3.5 cleanup" before contract sign-off.
- **One concrete run-start accounting race remains.** `StartAiRunUseCase.execute` reads a `ready` run and commits `admitDemoRunStart` before checking provider permission and before the repository's atomic `beginStart` (`backend/src/modules/ai-runs/use-cases/start-ai-run-use-case.ts:72-89`). A concurrent cancel, competing start, or permission revocation can win after the read, so the run-start limiter can consume a slot for a run that never transitions to started. The per-owner/per-run unique event makes duplicate attempts idempotent (`typeorm-demo-admission-repository.ts:247-297`), but it does not prevent this false charge. Count only on the successful first start transition (co-locate admission with `beginStart`, or provide a safe reservation/release protocol) and add a PostgreSQL race test against cancellation and competing starts. Do not hold the limiter transaction across provider/runtime work.
- **Production wiring currently supplies the run-start gate, but the use-case API permits omission.** `demoRunStartAdmission` is optional and invoked with optional chaining (`start-ai-run-use-case.ts:62,77-78`); the sole production composition found passes `demoAdmissionRepository` (`backend/src/composition-root.ts:260`). Keep demo paths fail-closed if that dependency is ever omitted. The repository itself rejects demo starts when configured limits are absent (`typeorm-demo-admission-repository.ts:247-260`); this is distinct from the optional-port bypass.

## Seams checked

- Admission transactions use a consistent global -> digest -> network ordering, and use PostgreSQL time for fixed windows. The request-key digest is globally unique and not combined with network identity; network key ID/hash remain rate metadata. Key rotation is blocked while a live network window uses another key ID (`typeorm-demo-admission-repository.ts:86-147`). The single global advisory lock serializes anonymous admissions; these transactions contain database work only.
- New-owner readiness checks require the matching pending admission, active unexpired demo principal, no project/root/reference/reservation/removal/content state, then empty quota reconciliation and zero ready/reserved usage before session issuance (`backend/src/infrastructure/database/typeorm-demo-storage-bootstrap.ts:27-67`; create/complete flow above). This relies on the new UUID remaining private until completion; it is not an existing-account reset path.
- Regular sessions are resolved through the existing session use case and must pass CSRF; regular accounts return 409 without replacement. Exact same-origin middleware is mounted on the route, invalid cookies are cleared only when treating that request as anonymous, and the existing cookie is sent only on first successful creation (`demo-admission-router.ts:53-117`). Express trust proxy is set only from configured CIDRs or `false` (`backend/src/app.ts:166`); HTTP logging serializes only method/status (`:188-194`). No raw key, cookie, or IP appears in these inspected logging paths.
- This admission/run-start code adds no credit balance or provider dispatch path. The production composition wires the run-start limiter, while Task 3.1 provider-call admission remains the independent spending boundary. No live inference or credit-spend behavior was exercised here.

## Evidence needed before Task 3.3 closure

1. PostgreSQL concurrency: same digest from different networks yields one owner and one admission count; only the original successful response gets a cookie; duplicate pending/ready/failed replays never mint one; overlapping network-key rotation fails closed.
2. Storage readiness failure/crash leaves no issued session; expired pending/failed rows are removed by the Task 3.5 worker after restart without touching regular users or showcase state.
3. Run-start rate test proves only the first successful `ready -> started` transition consumes a slot; cancellation, provider-permission revocation, and losing concurrent starts do not burn one; retries for the same run do not count twice; an over-limit demo run never reaches runtime/provider dispatch.
4. HTTP evidence covers a valid regular cookie remaining unchanged, invalid-cookie replacement behavior under rate limiting, exact Origin/CSRF, trusted and untrusted proxy chains, and absence of cookie/key/IP values in logs.
