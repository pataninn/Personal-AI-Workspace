# Runtime metering preflight

**Status:** Read-only architecture input for upcoming Task 3.1. This is not Task 3.1 implementation or live-provider/deployment evidence. No inference request, provider spend, or deployment action was made.

## Finding

Task 3.1 can meter the direct provider at its HTTP-send boundary. It cannot safely meter paid Hermes runs from the ACP events currently exposed to the app. The pinned Hermes runner owns an agent loop behind one ACP prompt; the app receives a run status and assistant/tool events, not a trustworthy event for each actual inference request and its usage.

The smallest release-compatible path is:

1. Add a call-admission/reservation boundary to the direct provider immediately before the HTTP POST. Reserve a bounded maximum using an explicitly configured price version and hard input/output bounds before sending. The current direct adapter makes one request per project run and has no application retry loop.
2. For Hermes, add instrumentation at the actual provider-request layer inside the pinned runtime/bridge path, or keep credit-funded Hermes unavailable until that boundary is enforceable. A safely bounded whole-run reservation is acceptable only if the bridge enforces a hard maximum number of actual provider attempts, input tokens, output tokens, and retries across the whole run. The current max_iterations values do not prove those bounds.
3. Keep the reservation when provider transmission, cancellation, or usage is unknown. Release only the unused part whose non-use is known. Missing/invalid price configuration, missing hard bounds, or failed atomic reservation must prevent the first paid request.

This preserves architecture section 7.1: post-response usage is settlement evidence, not admission control.

Hermes project run: StartAiRunUseCase -> HermesAgentRuntime.startRun -> HermesBridgeClient create/poll/cancel -> deploy/hermes-bridge Run.work / AcpSession.prompt -> pinned Hermes AIAgent loop in OpenShell sandbox -> configured OpenShell inference route -> provider.

Hermes Home-planning run: SubmitHomeTurnUseCase -> HermesHomePlanningRuntime.start / planning-create + poll -> deploy/hermes-bridge PlanningRun.work / AcpSession.prompt -> pinned planning_acp_runner AIAgent loop -> configured OpenShell inference route -> provider.

OpenShell is not an additional live app inference runtime today. composition-root.ts:createAgentRuntime returns UnsupportedOpenShellAgentRuntime when AGENT_RUNTIME_MODE=openshell. The separate raw OpenShell bridge/profile is a keyless foundation/fixture; the app does not wire its ACP operations into a supported agent runtime. Treat future OpenShell-backed inference as a new route that must meet the same admission contract before enablement.

## Task 3.1 contract decisions

### Evidence limits for a whole-context input reservation

The exact NVIDIA model page describes Nemotron 3 Super as having context “up to 1M tokens.” Its official serving example sets `--max-model-len 262144` by default and says reaching 1M requires an explicit opt-in. This establishes model capacity, not the configured maximum of NVIDIA's hosted endpoint used by this app. The hosted inference schema exposes an exact `max_tokens` range of 1–32,768 (default 16,384), but does not publish the endpoint's input/context cap or how requests rejected for exceeding it are billed. The app can enforce its 16,384 output cap; this does not bound input.

Do not replace the direct-path hard input-bound prerequisite with a guessed `1,000,000` or `1,048,576` token constant. A full-context reservation could avoid local tokenizer parity only if an authoritative endpoint contract establishes the accepted input ceiling and bounds charge for rejected/oversized requests. The current official sources do not establish those guarantees, so direct paid inference remains fail-closed until the bound prerequisite is proven. The detailed pinned-runtime/source inventory and hash evidence are in [Task 3.1 runtime hook feasibility](task-3-1-credit-ledger/artifacts/runtime-hook-feasibility.md).

### Hermes all-send coverage

The feasibility artifact identifies the pinned Hermes primary and auxiliary OpenAI clients and finds that wrapping both HTTPX sync/async `send` methods would catch those known clients and their retry sends. That instrumentation alone is not a complete egress admission boundary: raw HTTP clients or sockets can bypass it, while the existing egress policy permits other POST paths to the inference route and does not require an app-issued admission result. A supported Hermes mode therefore stays fail-closed until every provider-reaching send is forced through an admission-enforcing existing gateway/path or an equally complete egress boundary is demonstrated. The HTTPX hook by itself does not enable paid Hermes.

Paid-runtime enablement prerequisites remain unmet and are not waived by completing offline ledger/admission code:

- **Direct provider:** pin the exact provider endpoint and model; obtain an authoritative numeric maximum for input tokens at that endpoint (or a verified tokenizer/bounder for the exact serialized request); establish that provider-side templates/augmentation cannot exceed that bound or are included in it; enforce the output cap in the request; and configure operator-supplied versioned rates. A whole-context reservation also needs endpoint evidence that oversized/rejected requests cannot incur input charges beyond the reserved ceiling. The current “up to 1M” model page does not meet this gate.
- **Hermes:** demonstrate that every allowed route from both project and planning runners requires app admission before provider transmission, including retries and auxiliary calls; raw clients/sockets and alternate endpoints must be denied or pass through the same admission gate. Bound input/output and reserve each actual attempt (or prove a bounded whole-run envelope), then correlate settlement/unknown usage by stable per-attempt IDs. The inspected HTTPX wrappers and current egress policy alone do not meet this gate.
- **Release acceptance:** keep paid live inference disabled until the endpoint/path gates above, real configured price inputs, and offline concurrency/failure tests all pass. No provider call, price assumption, endpoint-profile assumption, or deployment claim is made by this preflight.

- **Direct path:** reserve after request validation and before each actual POST. The decision must be atomic against account daily/lifetime budgets and applicable demo daily/campaign budgets. A denied/missing admission means no call to fetch. Carry a stable run/call/attempt key to make retries and settlement idempotent. Enforce explicit input and output maxima at the provider request boundary; existing byte ceilings and ceil(bytes/4) estimate cannot be relabelled as token maxima.
- **Hermes path:** the app's single create/planning-create is early enough to reserve one whole-run envelope, but only if the bridge/model-call layer enforces that envelope at every actual inference attempt. It must count actual calls (including internal retries), cap each request's input/output, reject any call after budget exhaustion, and return per-call start/result/usage-or-unknown events with stable IDs. If the pinned runtime cannot be instrumented at its actual provider-send seam, block credit-funded Hermes admission; do not substitute the synthetic ACP run event as per-call admission.
- **Retries and loops:** account and reserve per actual request attempt, not per user message or ACP prompt. The application direct adapter currently sends once. For Hermes, configure/verify internal retry and fallback behavior at the intercepted model client; any retry must consume its own reserved call or fit the pre-reserved envelope. The iteration limits alone cannot set the billable call ceiling.
- **Usage and uncertainty:** accept only validated nonnegative provider usage associated with one call key. Missing/partial usage after transmission, timeout, transport loss, response rejection, or cancellation remains reserved at the safe upper bound until reconciliation. A cancellation response confirms local/bridge shutdown only; it does not prove zero provider charge. Never release an uncertain reservation just because the run is cancelled or failed.
- **Pricing:** use only developer/operator-supplied, versioned model prices and a safe maximum-bound calculation. Do not hard-code guessed prices. If price/version, hard input/output/call/retry caps, or reservation storage/transaction is missing or unavailable, fail closed before transmission. Existing activity UI's COST_UNAVAILABLE remains correct until pricing/accounting is implemented.
- **Rollout:** no live inference/deployment is part of this preflight. Keep credit-funded Hermes disabled until an offline bridge test proves every model send is admitted and accounted; keep direct mode disabled for paid access until its pre-send reservation and missing-usage behavior are covered. This is an admission gate, not a claim about current deployment readiness.

## Required offline evidence for Task 3.1

Use fake providers/bridge/model-client hooks and deterministic configured prices; no live provider credentials or inference are needed.

1. Direct: missing price/bound or denied atomic reserve causes zero fetches; a valid reserve precedes exactly one send; usage settles once on duplicate event/retry; absent/partial usage and timeout/cancel retain the maximum reserved amount.
2. Hermes project and Home planning: synthetic ACP tool loop with multiple actual model attempts demonstrates a reservation before each attempt (or demonstrates one bounded whole-run envelope); second attempt after limit is denied; internal retry/fallback cannot bypass the hook; usage event IDs are unique and replay-safe.
3. Concurrency and accounting: simultaneous reservations cannot overspend user daily/lifetime and demo daily/campaign limits; settle/release is idempotent; unknown outcomes remain reserved; no price or ledger failure permits a provider call.
4. Bounds: reject over-limit input/output/request counts before provider send. Verify run timeouts and cancellation terminate work without releasing uncertain credits.
