# Runtime hook feasibility

**Date:** 2026-10-19
**Status:** Read-only feasibility; no application code, deployment, provider request, or dependency change was made.

## Finding

Hermes has an actionable provider-send interception point in the pinned runtime: wrap HTTPX's synchronous and asynchronous `send` methods before the upstream transport is called. Its primary OpenAI clients and auxiliary OpenAI clients both use HTTPX in the pinned configuration. A synchronous ACP request/response can carry a per-send admission decision back from the app before that transport sends bytes. This is feasible without treating ACP run status as billing evidence.

The configured Nemotron model has an official model-wide context ceiling of “up to 1M tokens,” but neither hosted provider exposes its actual deployed context setting in the API response or the checked-in route. A fixed 1,000,000-token input bound plus an explicitly configured output cap is a possible conservative bound if the contract accepts the documented model maximum for the pinned model name. It reserves the maximum for every attempt and can make ordinary budgets deny calls. It is not a measured prompt count or an endpoint-specific capacity attestation. The exact local tokenizer/template parity with either hosted endpoint remains unverified.

For primary clients, [AIAgent's client factory](https://github.com/NousResearch/hermes-agent/blob/v2026.8.27/agent/agent_runtime_helpers.py#L2403) funnels normal OpenAI client construction and rebuilds through `create_openai_client`, which creates `run_agent.OpenAI` at lines 2539–2541. Main clients default to `max_retries=0`; Hermes owns its outer rate-limit, 5xx, and transport recovery loops, which make a new client send on each retry. The factory is not the only relevant path: [auxiliary_client](https://github.com/NousResearch/hermes-agent/blob/v2026.8.27/agent/auxiliary_client.py#L203) has its own sync/async HTTPX builders and its own `_create_openai_client` at lines 239–270. Those clients also default SDK retries to zero, while Hermes owns auxiliary retry/fallback policy. Explicit callers may override those defaults. Every such physical HTTPX send can pass through a wrapper on `httpx.Client.send` and `httpx.AsyncClient.send`, after the SDK has serialized the request but before `send` reaches the underlying transport. Rebuilds do not bypass a class-level wrapper.

This matches the local route: `deploy/hermes-bridge/provider.py` fixes the provider/model and the project and planning runners execute one ACP session inside the sandbox. The host bridge's `AcpSession` already validates and transports request/response `_pai/project_tasks` and `_pai/home_tools` calls; the local runtime helpers use `client.ext_method(...)` and synchronously wait for the host result. The app currently polls bridge events every 300 ms and responds to project-task calls, but `HermesAgentRuntime` emits only a synthetic `provider.request_started` once the run reports `running`. That event remains post-start status, not admission evidence.

Current bridge network policy allows `POST` to `/v1/chat/completions`, `/v1/messages`, `/v1/responses`, `/v1/completions`, and `/v1/embeddings` for `inference.local`. A wrapper restricted to the fixed chat-completions model should be paired with narrowing that policy to the supported paid endpoint and rejecting every other model/API route. Otherwise another client/API mode could bypass the HTTPX OpenAI hook. The policy is still process/path egress control, not an app-credit-aware proxy; it does not cryptographically require an admission token on a chat-completions request. Therefore this design proves coverage of the pinned Hermes OpenAI send paths, not arbitrary user-approved raw network code or provider/gateway-internal retries. If Task 3.1 requires a sandbox-level guarantee against all raw HTTP clients, a gateway/proxy admission enforcement point is still needed; none was verified in the checked-in OpenShell gateway interface.

## Exact smallest bridge protocol proposal

The bridge runner should gate each physical provider send synchronously; a later ACP event alone cannot be the gate.

1. A shared `runtime/provider_credit.py` installs wrappers around both HTTPX `Client.send` and `AsyncClient.send`. For the supported route only, it parses the already-serialized JSON body, checks the fixed `inference.local/v1/chat/completions` URL and run-approved model, validates/clamps `max_tokens` to the server-supplied cap, and rejects unsupported paths, models, malformed bodies, fallback providers, or missing admission connectivity before calling the original send method. The wrapper must not log or forward prompt text, bearer headers, or owner IDs.
2. It requests host admission through the existing ACP extension pattern (`pai/provider_call_admission`). The request carries only the session ID, route/profile identifier, model, request path, output cap and input-bound version/value. It does not carry user/owner authority or the prompt. The bridge associates the request with the authenticated run and generates a UUID `callId`/`attemptId` for that physical send. Each Hermes loop retry or auxiliary attempt reaches the wrapper again and receives a fresh identity/reservation.
3. The host bridge emits a sequenced `provider-call-admission-request` event with the ACP request ID, generated call/attempt IDs, route metadata, and bounds. The app resolves owner/source from the persisted run, reserves through `IProviderCallCreditAdmission`, and returns a result using the bridge's run capability. The ACP result to the runner is exactly one of `{outcome: "admitted", callId, attemptId, reservationId, maxInputTokens, maxOutputTokens}` or `{outcome: "denied"}`. The runner sends only if the result validates and agrees with the request. Timeout, malformed/late response, cancellation, or ledger error fails closed. A late grant after the runner timed out must be reported as a known-not-sent attempt so the app can release it; a missing response must never be treated as approval.
4. The response stream wrapper tees bytes without changing content. It extracts provider `usage.prompt_tokens` and `usage.completion_tokens` from a complete JSON response or SSE usage chunk, then waits for a `pai/provider_call_usage` result before yielding end-of-stream. The bridge/app callback contains only `callId`, `attemptId`, `reservationId`, and validated counts. The backend settles idempotently. If response usage is absent/partial, the stream ends early, the call errors after send, or the settlement callback is unavailable, the maximum reservation stays held as unknown. No cancellation or timeout releases a transmitted reservation. Usage availability in the actual NVIDIA/Nebius streaming routes was not verified, so successful settlement cannot be promised for every call.
5. Configure both runners to one approved `chat_completions` route/model and disable model/credential fallbacks. Validate every request at the HTTPX seam anyway. The existing planning runner already pins `api_mode='chat_completions'`, disables fallback/credential pool, and passes an output cap at most 512. The project runner currently sets `max_iterations=24` but no provider output cap/fallback override; iteration count is not a provider-send cap. Restrict bridge egress policy to the supported paid route (and any required non-billable model-discovery GET) and ensure no other library/provider client is admitted by the profile.

The ACP event handler must cap pending requests/count and accept a result only for the same active run/capability/session and pending ACP request. The bridge-generated attempt identity is associated with that pending request; the sandbox cannot choose owner, reservation, price, or credit amount. The parent owns the backend runtime callbacks, repository transaction and ledger; this proposal adds no public endpoint or database access inside the bridge.

## Token bound options

NVIDIA's [official model page](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-super-120b-a12b) describes Nemotron-3-Super-120B-A12B as supporting context “up to 1M tokens.” Its [inference endpoint reference](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-super-120b-a12b-infer) allows `max_tokens` from 1 through 32,768. The official [serving instructions](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-FP8) show a 262,144 default `--max-model-len` and require an explicit opt-in for 1M. This makes `1,000,000` input tokens a possible conservative, model-wide bound when the exact model identity is pinned; reserve that full bound plus the operator-configured output cap on every attempt. This is an inference from model maximum context, not evidence that either hosted endpoint is configured to accept 1M. Actual hosted caps, any provider-side augmentation, and how rejected oversized prompts are billed are not documented by these sources. A stricter contract requiring per-endpoint config attestation still has an unresolved bound prerequisite.

NVIDIA's model guide documents `AutoTokenizer.apply_chat_template(..., tokenize=True)` for counting a prompt using that model's tokenizer. It also documents context/template flags, so a matching local implementation would need to pin the tokenizer files/revision and reproduce the same chat-template flags and all server-side message transformations. No such tokenizer dependency or image package verification was found in the pinned Hermes manifest; the local app has no verified Nemotron tokenizer in its direct dependencies. A transport hook can read the exact JSON request and enforce `max_tokens`, but reading JSON is not exact tokenization. A tokenizer integration is therefore a future improvement only after provider-template parity is established; `ceil(bytes/4)` remains an estimate and cannot be promoted to a bound.

## Offline proof plan and limitations

No real provider request is needed. A bridge test can construct sync/async HTTPX clients with a fake lower transport and a fake ACP client. Assert zero lower-transport sends on denied, missing, timed-out, malformed, wrong-model, wrong-path, and wrong-cap responses; one admission per physical send/retry; fresh bridge IDs; no raw prompt/credential/owner in the ACP event; usage settlement for complete JSON and SSE usage; idempotent repeated result; and reservation retention when usage is missing, malformed, callback fails, stream closes early, or a transmitted request errors. Run equivalent cases for primary, auxiliary sync, auxiliary async, and fallback/wrong-profile clients, then test the bridge ACP event/result lifecycle with a fake child process. Add a policy assertion that paid endpoints outside the supported route are denied. Use deterministic fake rates and fake usage only; label all evidence as synthetic.

Not established: exact hosted endpoint context configuration, token count parity, provider usage presence on streaming responses, gateway/provider-side retry or billing behavior after transport loss, actual full sandbox filesystem contents, and protection against arbitrary raw `requests`/socket calls outside the wrapped HTTPX model path. No provider call, credential inspection, container start, dependency install, service change, or application edit was made.
