## Decision

Treat the public showcase as a bounded, immutable PostgreSQL snapshot. Treat each visitor's editable workspace as a separate demo-owned copy, pinned to one published snapshot and created through the existing project, quota, root-mapping, and storage boundaries. Do not expose the administrator's project as a public project and do not let a showcase identifier authorize project access.

This keeps the canonical example independent of its mutable source project, keeps public reads away from owner-root path resolution, and uses the current PostgreSQL and managed-workspace stack without adding a service, object store, or general template engine. The developer-owned Task 3.4 contract must define the exact DTOs, database migration number, limits, routes, and error vocabulary before code is authorized.

## Showcase publication

### Snapshot shape and publication

Use immutable `showcase_versions` plus bounded snapshot-item/file rows, and a single current-publication pointer. A version records a generated version ID, creation time, manifest digest, and only sanitized public fields. Its content is independent of future source edits or later publication. Public readers resolve the current pointer or a still-retained version; they never resolve an administrator project ID.

The minimum useful snapshot is selected project display metadata, explicitly selected tasks and nested checklist items, selected project facts, and explicitly selected regular files. Use generated snapshot item identifiers and preserve only relationships needed to display/copy the selected items. Do not include source account/project/resource UUIDs in public payloads or the clone provenance. Each clone generates new UUIDs and remaps parent/child relationships.

Files may be stored as bounded PostgreSQL `bytea` rows alongside sanitized relative display paths, media metadata, byte length, and content hash. This avoids inventing a second shared filesystem namespace and prevents a public file route from joining an owner-controlled path. Require explicit finite total-snapshot and per-file byte limits before enabling publication. Keep each stored path relative and validated with existing path rules; never accept an absolute path or a caller-selected storage root. Serve active-content types as downloads (or as an octet stream), with `nosniff`; do not inline HTML/SVG. Render text using normal escaped UI output.

Do not silently retain an unbounded number of blob versions. The contract must specify bounded retained-version policy: keep the current version and every version pinned by a non-ready copy, prune only unpinned older versions, and reject publication if the configured retention cap cannot be met safely. A ready copy no longer needs its source blobs. Exact byte and version limits are operator inputs; no defaults or production values are asserted here.

### Admin preview and publish

Only an active administrator may preview or publish. The source selector contains active projects owned by that same administrator; the admin role does not provide cross-owner project/file access. The operator explicitly selects the eligible tasks, facts, and files. Do not add automatic publication, cross-account browsing, policy editing, or a hidden sample project.

Preview and publish must share one allowlist serializer. Preview shows the exact data and file contents/names that a visitor would receive, along with exclusions. Publish takes the preview manifest digest and source version/selection revision; the server re-reads/re-hashes the exact selected source through existing owner-scoped repositories and file gateways. If anything changed, return a safe stale-preview conflict and leave the current pointer untouched. If unchanged, insert a new immutable version and switch the current pointer in one database transaction. Concurrent publishers serialize on that pointer; neither edits nor deletion mutate already-published bytes.

Always exclude chats/messages, Home conversations, run histories and events, approvals/proposals/audit trails, sessions, API credentials, secrets, provider/account permissions, storage paths/root mappings, owner/project IDs, context selections/exclusions, and unselected tasks/facts/files. A field/path allowlist does not prove that operator-written text or a selected file contains no personal or secret data. The admin must review the exact preview before publish. No operator-provided content exists now; the initial state is unpublished/empty. Any development fixture must say it is sample-only and must never be inserted as the production current version.

### Public read surface

Expose a separate read-only showcase page and a narrow unauthenticated GET surface for the current published snapshot and its explicitly included files. `404 SHOWCASE_NOT_PUBLISHED` is the safe public empty state. Return only snapshot DTOs, synthetic item IDs, sanitized relative names, and approved content. Keep the showcase out of `Project`, chat, task-mutation, file-mutation, skill-run, schedule/job, and export routes. There are no public write endpoints. Passing a showcase/source ID to an owner-scoped API must still produce the normal non-disclosing not-found/forbidden behavior; it cannot grant access or create a project context.

## Demo copy and session handoff

### Pin one version

At new anonymous admission, pin the exact currently published version and a server-generated target project ID to a durable copy job associated with the new admission/owner. The publication check, copy pin, and new-admission transaction must be atomic with respect to the current pointer: a concurrent publish may affect later admissions but cannot change this visitor's pinned source. If there is no published version, reject with generic `503 DEMO_SHOWCASE_UNAVAILABLE` before creating a demo owner or consuming admission counters. Do not attach the latest snapshot to an older Task 3.3 admission that has no copy pin; it remains inaccessible for workspace entry and follows existing expiry cleanup.

Task 3.3's session response/cookie behavior remains unchanged. A successful identity admission may have a valid fixed-expiry cookie while content setup is pending; that does not make the workspace usable. Copy readiness is a distinct durable state with `pending | ready | failed` and a separate `retryAllowed` flag. Only `ready` exposes the project. Status responses include no source IDs, paths, host details, or secrets.

If the pinned snapshot includes files but the managed root is unavailable or fails Task 2.2 boundary validation, fail closed before account creation when the condition is known at admission; otherwise keep the new copy inaccessible and unavailable until repaired/reconciled. Do not omit files to make a partial copy, and do not fall back to `/workspace`, `RECOVERY_ROOT`, or temp storage. A fileless snapshot can be copied only with planning capabilities if the normal account setup supports no-file mode; report `fileAccess=false`. The process-visible marker does not prove the host bind source; Task 8.1 must verify actual mounts.

### Copy and recovery lifecycle

Use one durable copy record per admission with an immutable pinned version/digest, target project ID, per-item target IDs or deterministic mapping, phase, attempt state, and timestamps. No request body accepts an owner, source version, project ID, or path. Copy content only from the immutable snapshot, never from the live administrator project.

1. Persist the copy job and stable target identifiers before side effects.
2. After empty-account storage bootstrap, in a bounded PostgreSQL transaction, create the hidden target project using its previously reserved UUID, selected task/checklist/fact rows, and quota references atomically through their existing repository/quota contracts. The Task 4.1 project-insert trigger creates the clone's fixed default policy row in that transaction; verify the row exists before readiness. Create fresh context defaults; do not copy source `assistant_scope_policies`, policy revisions, or selected/excluded context.
3. For file bytes, reserve the maximum planned target growth with Task 3.2, write via the existing storage gateway under the server-derived managed project mapping, verify path/hash/size, then settle actual references. Never hold PostgreSQL locks over filesystem work. Retries reuse the same version, project/resource IDs, manifest, and reservations; inserts/writes are idempotent.
4. Verify the complete DB and file manifest before changing copy state to `ready`. Partial relational rows or files remain hidden behind a server-side demo-copy readiness gate. Every owner-content read/write, conversation/run/event stream, tool call, skill/job/export, and file route must enforce that gate; a client route guard is not sufficient. Allow only session resume/logout, copy status/retry, usage needed by the banner, and public showcase reads while copy is not ready.
5. A startup/maintenance retry may resume a durable pending job using the existing backend maintenance lifecycle; do not add a separate service. If a crash leaves an unknown filesystem result or unresolved reservation, mark the copy unavailable (`failed`, `retryAllowed=false`) and keep the account storage unavailable until Task 3.2 reconciliation proves the outcome. Only a known safe failure may be retried. Do not blindly repeat an ambiguous file write.

Suggested authenticated status and retry operations are intentionally separate from `POST /api/v1/demo/session`: status is a read for the current cookie; retry is a CSRF/Origin-protected, same-owner action against the existing durable copy. A cookie-less idempotency replay stays status-only and can never mint a cookie. Retry does not create an owner, change the pinned version, alter credits/counters, reset or extend the 24-hour expiry, or open partial content. Concurrent retries return/observe the same copy job. The contract should make retry attempts finite and expose only generic `retryAllowed` state.

Leave a narrow snapshot-source extension point for Task 6.2 to provide selected persisted skill definitions later; that task must define its allowlist, version, quota, tool intersection, and fresh clone IDs before skills enter a published version. ## API, UI, and failure semantics for the contract

These names are architecture suggestions; the Task 3.4 developer contract/OpenAPI owns the final names and must keep the same behavior:

| Situation | Required behavior |
| --- | --- |
| No current showcase | Public current view returns `404 SHOWCASE_NOT_PUBLISHED`; Try demo is unavailable. New admission returns generic `503 DEMO_SHOWCASE_UNAVAILABLE` before creating an owner/counter. |
| Current demo identity has copy pending | Cookie-authenticated status reports pending; show preparation state and no project content. |
| Copy ready | Status reports ready; then and only then may the private project surface open. |
| Safe, known copy failure | Status reports failed with `retryAllowed=true`; authenticated retry reuses the same pinned version and IDs and returns/continues pending. |
| Unknown quota/filesystem outcome or missing/unsafe managed root | Status is unavailable/failed with `retryAllowed=false`; no partial content and no retry button until reconciliation/repair proves it safe. Return only generic `503 DEMO_COPY_UNAVAILABLE` where an action cannot proceed. |
| Permanent failure, expired demo, or copy cannot be retried | No workspace access; generic conflict/unavailable response (for example `409 DEMO_COPY_NOT_RETRYABLE`); Task 3.5 cleanup remains authoritative. |
| Regular session calls demo admission | Preserve Task 3.3's `409 DEMO_REGULAR_SESSION_ACTIVE`; never replace the regular cookie. |
| Anonymous same-key replay | Preserve Task 3.3 status-only response; never recover a cookie or resume a private session. |
| Publish preview is stale | `409 SHOWCASE_PREVIEW_STALE`; current publication is unchanged. |
| Admin selects a foreign project | Non-disclosing not-found/forbidden result; no cross-owner source access. |

No error includes raw paths, source IDs, owner IDs, IPs, quotas, provider details, or internal exception text. UI text may say the demo/showcase is unavailable without exposing whether the host mount, counter, reservation, or file scan failed.

## Required verification handoff

- **API/database:** Test unpublished admission creates no owner/counter; concurrent admission pins one version once; two simultaneous publishers do not produce a mixed snapshot; stale preview leaves the old version current; all copied rows get new IDs and owner links; source IDs/private conversations/proposals/context/policies never enter public payloads or clones; version pruning never deletes a pin still needed by a non-ready job.
- **Isolation/read-only:** Test public GET without a session, direct HTTP mutation attempts against version/item IDs, workspace tools/chat/jobs/exports, foreign admin source IDs, and owner endpoints given showcase IDs. Every mutation must deny server-side. Test copy-pending denies every private workspace data/stream/tool route.
- **Quota/filesystem:** Use an isolated configured test root with trusted marker, not the live `/workspace`; verify reservations before writes, exact file hashes/sizes, duplicate retry idempotency, symlink/traversal rejection, partial-write recovery, quota rejection, and unknown-outcome fail-closed behavior. Prove target copies are accounted to the demo owner while the shared curated snapshot is not.
- **Crash/retry:** Restart after pin, relational commit, each file write, reservation, and settle-before-ready. The same pinned version/target IDs must resume without duplicate rows or bytes; unresolved operations remain blocked until reconciliation.
- **Browser/network:** Two isolated browser contexts receive different owner/project/task/fact/file IDs and cannot change one another or the source project. Verify one-click entry, regular-session conflict preservation, fixed expiry, retryable/terminal copy states, read-only showcase attempts, mobile banner and exhausted-credit state. Inspect DevTools responses for private source data, credentials, owner paths, and session recovery. No browser or network evidence is collected by this preflight.
- **Deployment boundary:** Application tests can prove path/mapping behavior for injected fixtures. They cannot prove `/account-workspaces` is a physical host bind or persistent across deployment restart. Task 8.1 must verify Compose mount source/target, marker, restart, backups, and free-space alert settings. No live deployment or provider claim is made here.
